# 2026-08-26, overnight — two os9exec defects, and source for 62 more programs

rdoggett went to bed with standing permission to commit on the branch and to
install or replace anything that came out better. This is what happened.

## The headline: two os9exec defects, both with minimal reproductions

Both were found by running programs, which is what he said the point was.
Both have the same shape: **the statically-linked build is correct and the
cio trap-handler build is not.**

1. **`F$SRqMem` is handed a pointer where a byte count belongs.**
   `notes/OS9EXEC-CIO-SRQMEM.md`. Twelve lines of C (`putchar` 4000 times)
   built `-qixm` makes 4001 memory requests of 413,256 bytes each, never
   returns one, exhausts the 32 MB arena, and prints os9exec's own
   "No more memory !!!" into the program's output. Proven to be an address by
   rebuilding os9exec with a different `D_BlkSiz`: the "size" moved exactly as
   far as the heap did. `card`'s bus error is the same runaway from the other
   end.

2. **cio's stdin never returns end-of-file.**
   `notes/OS9EXEC-CIO-STDIN-EOF.md`. Nine lines (`getchar` to EOF) built
   `-qixm` hangs forever; built `-qm` reads its 37 bytes and exits. This eats
   filters -- anything that reads to end-of-file.

Reproductions and traces are in `notes/cio-srqmem/`.

**Neither is a reason to move off cio.** cio remains the driver's default and
Microware's permission to ship it stands. Two recipes carry `TRAPFREE` as a
workaround with a comment saying so, and they should lose it when os9exec is
fixed.

## Two conclusions of mine, withdrawn

**`travesty` is not damaged and its output was never wrong.** I said twice
that it "reproduces its input verbatim" and called it a broken port. It
produces no output at all when built with cio -- it never finishes reading --
and what I measured was os9exec echoing the redirected stdin to the console.
The tell was there and I missed it: the "output" was exactly the length of the
INPUT and ignored the flag that sets output length. Built `TRAPFREE` it works,
at the archive's source, unmodified.

**`NOCURSES` was a flag invented for a cause that does not exist.** I had
measured three of the four cells and read a cause into the gap. `-qm` works
WITH curses linked. The flag is gone and `rebuild.sh` is byte-identical to
what it was.

## Source coverage: 392 -> 626 of 939 programs (41% -> 66%)

**234 programs gained source tonight**, none of it downloaded -- all of it was
already in the hoard, inside archives nobody had ever unpacked.

**The tool that found it is new.** `tools/index_archives.py` lists what is
inside every archive in the hoard without extracting any of it, and
`tools/find_missing_source.py` crosses that against the programs with no
source here. A `find` cannot answer this question; it only ever sees what
somebody already unpacked. The index is `notes/pool-archive-contents.tsv`:
352 archives, 15,693 members.

**Every installed source was proved, not guessed.** Where the archive carried
a binary too -- which most did -- it was compared with ours byte for byte, and
only byte-identical matches were installed. `unzip`/`funzip`/`zipinfo` were
matched instead by the exact OSK version string our binary carries
("OSK Version 1.1 By Ricky Beam 10/16/93"), which distinguishes
`unzip50_src.lzh` from the older `unzip_src.lzh` sitting beside it. That
caution is not theoretical: this repo has already shipped a recipe pointing at
the wrong `pep`.

**The biggest single find was netpbm: all 169 of them, in one archive.**
The disk ships 169 netpbm converters -- 18% of everything on it -- and had
source for none. The OSK port's own `ReadMe.OSK` says the author split it into
`netpbm_cmds.lzh`, `netpbm_docs.lzh` and `netpbm_src.lzh`. In this pool those
names are CROSSED: `netpbm_src.lzh` holds no source at all, just 196 man pages
(22 of which were missing from `DOC/netpbm` and are now in), and the real
source is a 1.25 MB LHa archive called **`osknet.readme`**. Nothing that
trusted a file extension could have found it; the indexer now sniffs content,
which is what turned 352 readable archives into 530.

Second find: **`sc`, the spreadsheet, had no source at all** and the
complete set is in `EFFO/pd8.lzh` -- sources, docs and a tutorial.
`notes/COMPILE-AUDIT.md` records exactly how far its build gets and what stops
it (`wrefresh`, defined twice in the overlay's `curses.l`).

## Three bugs fixed in our own tools

  - **`tools/verify_all.sh` was losing programs to the locale.** One `tr` and
    one `cut` lacked `LC_ALL=C`, so the capture pipeline aborted with
    "Illegal byte sequence" the moment a program emitted an 8-bit byte, and
    that program was then classified on nothing. The sweep was stopped and
    restarted twice tonight rather than collect data that could not be
    trusted.
  - **`tools/rebuild/shims/os9randint.c` was LF-terminated** and could never
    have compiled. Fixed -- and fixing it showed the shim is also unnecessary:
    `LIB/unix.l` already has `randint`.
  - **`index_archives.py`'s own lha parser** read every data row as a rule
    line, because an lha listing starts each row with its permission field
    `----r-wr`. 40 archives indexed as empty. Both that and the two locale
    bugs are the same failure: a check that could not fail.

## A method worth keeping

Where an archive carried a binary as well as source -- most did -- the source
was installed only if that binary was **byte-identical** to ours. Where it did
not, the test was to pull the distinctive printable strings out of OUR binary
and look for them in the candidate source. `makeinfo` scored 75 of 210 and
`upperdir` 6 of 11; twelve others scored 0, 1 or 2 and were REFUTED and
written down in `notes/COMPILE-AUDIT.md` so the next pass does not re-chase
them. A name match is a lead, not a finding -- this repo has already shipped a
recipe pointing at the wrong `pep`.
