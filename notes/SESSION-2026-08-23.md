# 2026-08-23 — blarslib, and what it unlocked

Branch `release-pass-2026-08-21`. Nothing pushed. Eleven checks green.

## blarslib

rdoggett said yes, minus the Microware headers. In as
`SRC/blarslib` + `DEFS/blarsdefs` + `LIB/blarslib.l` (32 of its 36 objects).
Thirteen of its headers were byte identical to Microware's or near enough and
did NOT ship; `DEFS/blarsdefs` carries one-line forwards of our own instead.
Those forwards must include BY ABSOLUTE PATH — `<sgstat.h>` from inside
`blarsdefs/sgstat.h` finds itself, and cpp opens it until it runs out of paths.

Four objects are out: `stat.c` (wants `sys/types.h` to define `dev_t` as a
struct, and the overlay's is `SRC/COMPAT`'s, which deliberately does not),
`ftime.c`/`makenv.c`/`putenv.c` (`time_t`, hidden behind `#ifndef ctime` in the
SDK's `<time.h>`), `gethostname.c` (a quoted `-D` the OS-9 shell will not
carry).

## What it unlocked

  - **uucp_blars** — all five programs. `uuxqt` also needed `pw_giduid`, OS-9's
    single packed group.user id, which our `pwd.h` did not have and blarslib's
    `getpw.c` never set.
  - **uucpbb** — 21 of 24. Out: `login` (wants an `<os9.h>` nothing here has),
    `chown` and `cnvrtmail` (assign to `fd_own`, an ARRAY in this `<direct.h>` —
    a port written against a version where it was one number, and not something
    to guess at in a program that changes ownership).
  - **smail 2.5** — all four. `SRC/COMPAT/types.h` is new: the SDK's
    `<types.h>` stops at `u_char` and friends, so `off_t message;` in
    `deliver.c` failed as a declaration and reported as `message` undeclared
    forty lines later.
  - **SB-Prolog** — its makefile builds `builtin/` as a library first; naming
    those sources alongside the simulator's comes to the same thing.

## Not unlocked, and why

  - **macutils** — needs `struct stat` as blarslib declares it, and there is no
    way to give two trees a different `<sys/types.h>`: cpp will not search a
    `-V` directory for an include name with a directory in it. This was the
    argument for taking blarslib in the first place, and it did not hold.
  - **gtar** — everything else is in place now, including a generated
    `testpad.h`, but `cpp` bus-errors on `tar.c`. Same defect as `flex`:
    `notes/CPP-MACRO-CRASH.md`. Two victims now, not one.

## Where the build stands

**271 of 274 recipes build clean** (measured 2026-08-23, whole tree, after the
`COMPAT/types.h` change). The three are `ls` (gcc2), `pdraw` (X11) and `pep`
(the EPROM board's own library). Recipes went from 203 at the start of this
pass to 274.

## Two lessons, both paid for twice

**Do not put a fix in `SRC/COMPAT` when one tree needs it.** `smail`'s
`deliver.c` wants `off_t`; adding it to a new `COMPAT/types.h` looked tidier
than a define and broke `less`, which `#define`s `off_t` itself -- so
`typedef long off_t;` became `typedef long long;`. It is `-Doff_t=long` in
smail's recipe now, scoped to the one tree.

**Do not edit anything a build reads while it is running.** The full build
that caught the `less` regression then reported two more failures that were
only the tree changing underneath it. A run measures the state at the moment
each recipe is reached, not at the start.

## Also

`tools/rebuild/tidy.sh` — puts `disk/` back after a build, touching only files
a build could have made. Twice a hand-typed `git checkout -- disk/SRC` took
deliberate source fixes with the object files.

# 2026-08-23, later — the cpp limit, measured; djpeg builds

A second session the same day, picking up `PLAN-next.md` item 1a: the four
programs stopped by Microware's `cpp`.

## The headline: the cpp bug is a 512-character line limit

Not nested macro expansion. **`cpp` edition 37 bus-errors on a source line of
513 characters or more**, and `c68` refuses one of 1023. Both measured by
feeding each tool one-line files of rising length. It explains the three-file
reproduction this collection has been carrying since 2026-08-22 exactly:
`crash5.c` expands to 542 characters and crashes, `ok4.c` to 270 and
`ok5tiny.c` to 222 and both compile. Five levels of nesting was never the
point; 542 was.

`notes/CPP-MACRO-CRASH.md` is rewritten around that. Its filename is now a
misnomer and is kept because six other files point at it.

**A trap inside the trap.** `cpp` does not always crash on an over-long line —
in some shapes it truncates its output and exits with no diagnostic. An
earlier pass over this same question read those silent truncations as passes
and concluded long lines were fine. Distrust a quiet `cpp`; measure the `.m`.

## djpeg builds, and decodes

`disk/SRC/jpeglib` had `cjpeg` and not `djpeg`, because `jdmarker.c` is a
victim of the above. It needed `KNR` **and** `CPP2` at once — ANSI source
whose one long line kills the preprocessor — and the driver could only do one
or the other. It can do both now, ansi2knr first because cccp2's output is no
longer C that ansi2knr could read.

Verified by running it, not by linking it: `cjpeg` compresses a generated
96x64 PPM, `djpeg` decompresses it, and the two ramps come back at a mean
error of 1.1 and 1.5 of 255 while the deliberate high-frequency channel comes
back noisy. That is a JPEG decoder behaving correctly. `sips` on the host
reads the intermediate as a 96x64 JPEG, so `cjpeg`'s half is honest too.

**The tree's own test images cannot be used** and this is worth knowing before
someone tries: `testorig.jpg`, `testimg.jpg` and `testimg.ppm` in
`SRC/jpeglib/JPEG_5A` have **no byte at or above 0x80 anywhere** — 26,574 of
the PPM's 103,639 bytes are `?`. They went through a 7-bit transfer long
before they got here. `djpeg` on `testorig.jpg` says `Not a JPEG file: starts
with 0x3f 0x3f`, which is the file's fault, not the program's.

## Four changes to the build driver

  - **`KNR` and `CPP2` compose.** Either alone still means what it did.
  - **`KNR=a.c,b.c`** translates only the sources named. `ansi2knr` is safe on
    an ANSI tree and NOT on a K&R one: given `wildmat(s, p)` with the
    parameters declared on the following lines it emits
    `wildmat(s, p)  s; p;` and adds bogus `int` declarations. A blanket `KNR`
    left gtar worse than it found it.
  - **A recipe's `-V=<dir>` reaches the GNU preprocessor**, translated to
    `-I`, and goes in ahead of `/h7` and `/dd/DEFS`. Before this a `CPP2`
    recipe's include directories were silently dropped and every header in
    them came back "file not found".
  - **`cpp2_fixup` re-wraps over-long lines**, and only ever cuts at
    whitespace OUTSIDE a string literal. Both of the usual ways to split a
    literal were tried on `c68` and both fail: `"a" "b"` concatenation is
    ANSI, and a backslash-newline inside a literal is spliced in translation
    phase 2 — which for a `.m` file already happened, in the preprocessor
    being replaced. A line with no safe cut is left long, because
    `input line too long` is a diagnostic and a literal broken in half is a
    mystery.

## Four headers into SRC/COMPAT

`sys/ioctl.h` and `grp.h` and `bcopy.h` forward to headers the disk already
has; `sys/sysmacros.h` is the three device-number macros. Each says in its own
header why it exists. All four are new names — nothing that compiles today can
start resolving differently because of them.

Deliberately NOT added: `sys/mtio.h`. There is no tape ioctl here, and every
use of one in gtar is guarded on `MTIOCTOP`, so leaving it undefined compiles
the right code out.

## Three source lines changed, in gtar, and marked

`create.c:to_unix_mode`, `list.c:to_os9_format` and `buffer.c:rmt_jl_open` were
ANSI definitions — all three additions by the OSK porter rather than FSF code
— and are K&R now, each with a two-line comment saying so and why. This is the
`jconfig.h` precedent: a portability fix, made in place, marked where it was
made. `ansi2knr` could not do it without wrecking the rest of the tree.

## gtar: where it actually stands

Not built. But nothing about the preprocessor is in its way any more, and what
is left is named rather than mysterious — `ERROR`, `TRUE`/`FALSE`, `S_IFREG`
and the Unix `errno` family are undeclared. `notes/CPP-MACRO-CRASH.md` has the
full state, including the two hours that prove `DEFS/os9lib` is a dead end for
this toolchain. Its recipe is deliberately NOT in `recipes.psv`: a recipe means
"known to compile".

## inform builds, and it is exact

`inform` -- Graham Nelson's Inform 1.0 (v796), the Z-machine compiler that
produced everything in `GAMES/INFORM` -- has never been built here.
`DOC/INDEX` has carried "this SDK's cpp aborts partway through" for months.

It now builds, and the proof is not that it links: **it recompiles the
collection's own `hellow.inf` to a story file byte-identical to the
`GAMES/INFORM/hellow.z3` that has shipped since day one.**

Three blockers, none of them what the notes said:

  1. **cpp's 512-character line.** informosk.c has one logical line of 775
     characters. `CPP2` clears it.
  2. **`SRC/COMPAT/limits.h` was unusable in a `#if`.** It derived every limit
     through a cast -- `#define INT_MAX _S_MAX(int)`, which expands to
     `((Signed int)((unsigned int) ~0 >> 1))`. That is correct C and always
     zero in preprocessor arithmetic, which has neither casts nor types. ANSI
     requires these macros to work in `#if` for exactly this reason. inform
     selects its 32-bit integer type with a four-arm `#if` over `SCHAR_MAX`,
     `SHRT_MAX`, `INT_MAX` and `LONG_MAX`; every arm was false and it reached

         #error No type large enough to support 32-bit integers.

     The header is plain constants now, MEASURED on this toolchain rather than
     assumed: char 1 byte and signed, short 2, int 4, long 4, pointer 4.
  3. **`o68` miscompiles what `c68 -k` emits** -- below.

## The o68 bug

100K of code cannot reach all of itself with the 68000's 16-bit BSR
displacement, so `r68` says `**** error - branch out of range ****` once per
call. `c68 -k` (force long PC-relative references) is the answer -- and then
`o68`, the object-code improver, silently corrupts string literals.

A ten-case probe, everything built with `-k`, once with o68 and once without:

| construct | with o68 | without |
|---|---|---|
| plain literal | ok | ok |
| **`?:`, TRUE arm** | **wrong** | ok |
| `?:`, FALSE arm | ok | ok |
| **assigned from `?:`, TRUE arm** | **wrong** | ok |
| assigned from `?:`, FALSE arm | ok | ok |
| array of literals | ok | ok |
| function returning one | ok | ok |
| `switch` | ok | ok |
| `if`/`else` | ok | ok |

So it is exactly one construct: the true arm of a conditional expression
choosing between two string LITERALS gets an address eight bytes past the
right one. `one ? "Error" : "Warning"` prints `rning`.

That is what inform was doing. It reported two impossible diagnostics against
every source it compiled -- "Names are not permitted to start with an _"
against a `for` loop -- and finished `Compiled with 2 errors and 0
warningsput)`. Both messages come through `?:` on literals.

**`LONGREF`** is the recipe flag: `c68 -k`, and no `o68` pass. The two cannot
be separated, so they are one word. Dropping o68 costs some optimisation and
nothing else; `r68` assembles c68's output directly. On the ordinary `cc` path
the equivalent is `-K=0CL`, and it needs `-O` for the same reason.

## The strchr(s,0) grep — done, and the guidance was too broad

`FOR-RDOGGETT.md` has said since 2026-08-21 that *any* `strchr(s, 0)` here is
a latent bus error. Measured:

    strchr(s, 0)   unix.l   -> end-of-string   CORRECT
    index(s, 0)    clib.l   -> NULL            wrong
    strrchr(s, 0)  unix.l   -> NULL            wrong
    rindex(s, 0)   clib.l   -> NULL            wrong

`clib.l` has no `strchr` at all, which is why 27 trees here `#define strchr
index`; a `-qm` build takes `strchr` from `unix.l`, and that one is right. So
the idiom is fatal only where the tree ALSO macros it onto `index`.

Whole-tree grep: seven call sites. Six are pdksh's, which does macro it, and
**all six are already covered** by `sh_eval.c.patch`, `sh_history.c.patch` and
`sh_lex.c.patch`. The seventh is `tess/parser.c`, which does not macro it and
so gets the correct function. Nothing to do. Item closed.

## gtar — stopped deliberately, and now fully characterised

Everything blamed on the preprocessor is cleared and committed: `CPP2` plus the
line re-wrap gets all nineteen sources through `cpp` and `c68`, `-DUSG
-DNO_REMOTE -DVARARGS_MSG` are the right switches, four headers went into
`SRC/COMPAT`, and its three ANSI definitions are K&R.

What is left is a PORT DECISION, not a header hunt. The complete undeclared

    errno EBADF ENOSPC EIO ENXIO EPIPE ENOENT EEXIST

    TRUE FALSE  /  ERROR  /  time_t, struct timeb

`S_IFREG` is the wall. OS-9 has no regular/character/block distinction and no

Ruled out, so nobody repeats it: `DEFS/os9lib` has every missing name and is

## ed builds — and it was never an ANSI tree

`COMPILE-AUDIT.md` has listed `ed` under "ANSI C" since the category was
written. **It is K&R throughout**, and running `ansi2knr` over it is actively
destructive: `get_sbuf_line (lp)` comes out as `get_sbuf_line (lp)  lp;`. The
audit is corrected.

What actually stopped it was the one thing the README already knew and had
filed under a different heading: `ed.h`'s `REALLOC` macro joins into about
1400 characters, and cpp's limit is 512. `CPP2` clears it, and then the rest
was ordinary work:

  - **`ERANGE`** — the SDK's `<errno.h>` is OS-9's own error numbers and has
    none. `0x100` is the value `DEFS/os9lib/errno.h` gives it, so a caller
    that got it from there and one that got it from the recipe agree.
  - **Three of its own sources were missing from the recipe** —
    `alloca.c`, `xmalloc.c`, `error.c`, all named in its Makefile's `LIBSRCS`.
    The lesson the audit already records: read the tree's own makefile.
  - **`strtol` is in no library a trap-free link can use.** `csl.l` has it and
    needs the trap handler; `ppplib.l` has it and `l68` rejects the file as
    "not a relocatable module". So `shims/os9strtol.c` is new — full ANSI
    behaviour including the end pointer and the ERANGE report, which are the
    two things `atol` cannot do and the only reasons ed wants strtol at all.
  - `os9lib.l` for `umask` and `alloca`, `blarslib.l` for `vfprintf`.
  - **`size_t`.** `xmalloc.c` writes `size_t n;` in a K&R parameter list
    having included only `<sys/types.h>`. `SRC/COMPAT/types.h` supplies it
    now, guarded with `_SIZE_T` — **the SDK's own guard name**, from its
    `<stddef.h>` and `<stdlib.h>`, so whichever header a file reaches first
    the other stands down. `-Dsize_t=unsigned` was tried first and is exactly
    the trap that file's header comment already warns about: it turned
    `typedef long size_t;` into `typedef long unsigned;`.
  - `ed/regex.h` carried an unguarded `#ifdef OSK typedef long size_t;` — the
    porter's line, not the FSF's. It has the `_SIZE_T` guard now, marked.

diagnostic anywhere. The main()-finding loop took the LAST source that matched,
not the first. It takes the first now, which is the source a recipe names

## mtools, and the real limit of the KNR flag

`PLAN-next` said mtools "times out at the 30-minute limit, or fails with an
empty log. Worth one careful run." It was run, it finished in minutes, and it
is not a timeout at all: **c68 rejects prototypes on nearly every line**, and
`ansi2knr` did not touch a single definition.

**ansi2knr's own header says why, and it is a CODE STYLE rule, not a header
rule:**

> ansi2knr recognizes functions by seeing a non-keyword identifier **at the
> left margin**, followed by a left parenthesis ... the function name must be
> the first thing on the line.

JPEG writes `METHODDEF(void)` on one line and `start_pass (j_compress_ptr
cinfo)` on the next — name at the margin, so ansi2knr converts it. mtools
writes `static void bad_country_file(void)` all on one line, which begins with
a keyword, so ansi2knr skips it and every prototype reaches c68 intact.

Counting headers whose name is at the left margin against those that start
with a keyword:

    JPEG_5A       348 /  12     ansi2knr reaches it
    MTOOLS_3.6      3 / 477     it does not
    lua/SRC         1 / 236     it does not

That is the correct statement of the KNR flag's limit, and it is sharper than
"the tree's config header has to stop declaring prototypes" (which is also
true, and secondary). **Caution: the count alone does not settle it** — `ed`
scores 118/0 and is not an ANSI tree at all, because a K&R definition has its
name at the left margin too. The count says whether ansi2knr will TOUCH a
tree, not whether it will help.

mtools' OSK port is a `gcc2` build (`CC = gcc2`, `-I/h0/mwos/src/defs/GCC2`),
same as `ls`. That is its real category.

## rayshade builds, and RENDERS — the first package build here

78 sources across six nested libraries. Four separate walls, each measured:

  1. **`<libcommon/common.h>` — a DIRECTORY in the include name.** Microware's

     straight to `/dd/DEFS` and fails. This is recorded in `COMPILE-AUDIT.md`

     **GNU cpp has no such limit**, so `CPP2` dissolves it — every one of

## macutils — the audit's reason was right and is now obsolete

`COMPILE-AUDIT.md`: *"blocked on an include-path knot: it needs `struct stat`
as blarslib declares it, and cpp will not search a `-V` directory for a name
with a directory in it, so two trees cannot have a different
`<sys/types.h>`."* Both halves true; `CPP2` dissolves both, because GNU cpp
does search `-I` for such names and a recipe's `-V=` now reaches that pass.
`binhex` and `unsit` build. `mcvert` wants `ftime()`, one of the four blarslib
objects deliberately not taken; `macsave` and `macunpack` are not run down.

## A driver bug this found: same basename, silently clobbered

`binhex` names **both** `BINHEX/binhex.c` (the program) and `CRC/binhex.c`
(its CRC table). The driver derived every temporary from `basename`, so both
became `ctmp_binhex` — the second overwrote the first, and the link then
reported `Symbol 'main' unresolved` with nothing anywhere to say why.

**The first fix was flattening the path** -- `../CRC/binhex.c` ->
`CRC_binhex` -- and it was WRONG, in a way worth recording because it took a
whole-tree build to catch:

    ctmp_libray_LIBCOMMON_expr.raw          31 characters

**An OS-9 filename may be at most 29.** Measured the same day, by creating
names of each length in turn: 29 works, 30 does not. cccp2 could not create
its output, said `file not found` -- about the file it was trying to WRITE --
and the shell's abort-on-error ended the run at the first source. `rayshade`
went from building to not, and `tools/build.sh rayshade` reported it in under
two seconds.

`tmpbase()` suffixes only on an actual collision now: the first `binhex` keeps
that name, the second becomes `binhex_1`. Every other recipe's temporaries are
byte-for-byte what they were, which is the property that makes the change safe
across 288 recipes.

The plain-cc paths cannot do even this, because there `cc -r` names the object
after the source and the collision is cc's rather than ours, so a
same-basename recipe needs `CPP2` for now.

**Two lessons, and the second is the collection's own.** A fix verified on one
recipe is not verified; and the error a tool reports may be about the file it
is WRITING, not the one it is reading.

# 2026-08-23, after the question — "how did these ever compile?"

rdoggett asked the right question about the in-place source fixes: if they are
needed to compile, how did the ports work on OS-9 originally?

**They were compiled with GCC, not with Microware's `cc`.** Their own makefiles
say so:

    gtar        CC = gcc
    rayshade    CC = gcc,  -mlong-calls
    mtools      CC = gcc2
    jpeglib     CC = gcc2

GCC is ANSI, so `to_unix_mode( int wert )` was never a problem for it; it has
no 512-character line limit, so tar.c's usage string was fine; and
`-mlong-calls` is exactly the flag for rayshade's 39 KB stack frame -- the
porter hit that wall too and had an answer for it.

So **most of the night's source edits work around the wrong compiler**. Sorted
honestly:

  - gtar's three K&R conversions -- compiler workaround. Confirmed below.
  - rayshade's MAXMODELDEPTH 128 -> 48 -- compiler workaround.
  - rayshade's `lex.c` `void free()` -- almost certainly the same.
  - rayshade's `CPPSTDIN "cccp"` -> `"cccp2"` -- **NOT** a compiler issue. A

## The disk's own gcc2 could not compile a two-line program

`disk/CMDS/GCC2/` is a complete GCC 2.5.6 -- `gcc`, `gcc2`, `gpp`, `cc1plus`,
`cc2`, `cccp2`, `collect`. It runs, and its output is trap-free and carries no
author stamp, which are the collection's two hard requirements.

But this did not compile:

    #include <ctype.h>
    #include <stdlib.h>
    main(){return 0;}

Two faults, both in `DEFS/GCC2/stdlib.h`, and both now fixed in place:

  1. It includes `<stdio.h>` and then `<direct.h>`. Under gcc2 `<stdio.h>` is
     `DEFS/GCC2/stdio.h`, GCC's own, which does not typedef `WORD` -- and
     `direct.h` line 2 includes `<stdio.h>` precisely to get it. Every gcc2
     compilation that reached `<direct.h>` died with `parse error before
     WORD`. `DEFS/GCC2/stdio.h` typedefs it now, as Microware's does.
  2. It declares `extern int isalnum(char c);` and fifteen more like it, while
     the SDK's `<ctype.h>` defines those names as MACROS. Include ctype first
     and the declaration will not parse. They are `#ifndef`-guarded now.

**That is why `ls` was "repaired" rather than rebuilt, and why `mtools` and
`lua` were written off as gcc2 builds** -- the gcc2 on the disk was unusable
for anything that included two ordinary headers, and nobody had tried it on
something small enough to see why.

## What it does and does not unlock

With those two headers fixed, gtar's ANSI prototypes stop mattering -- the
files that failed on them under Microware `cc` get past gcc2 without a
murmur, which is the confirmation that those edits were compiler workarounds.

**But gtar still does not build under gcc2**, and it stops on the SAME names
it stopped on under `cc`: `TRUE`, `FALSE`, `ERROR`, `S_ISUID`, `EOS_CEF`,
`EOS_PNNF`. So the earlier conclusion -- *what is left is a port decision, not
a header hunt* -- holds whichever compiler is used. That is worth something:
two independent routes reached the same wall.

One new wrinkle, and it is ours: with `SRC/COMPAT` on the include path, gcc2
reports `tar.h:48: conflicting types for size_t`, because this session added
`size_t` to `COMPAT/types.h`. The COMPAT lesson keeps being paid for.

## Where a GCC recipe flag stands

Not built, deliberately. The prerequisite was the DEFS repair above, and that
is done and committed. What a `GCC` flag needs beyond it:

  - `gcc2 -c <src>` emits `<base>.r`, so per-source compilation works and the
    512-byte command line is not a problem.
  - The LINK must be `gcc2`, not `l68`: gcc objects carry gcc's own magic and
    `l68` will not take them (`notes/FREEWARE-REBAKE.md` recorded this for
    `ls`). A long object list on one line will hit SCF's 512 bytes for a tree
    the size of rayshade, and no response-file mechanism is known yet.
  - Include order is `-I` then `DEFS/GCC2` then `DEFS`, and a recipe's `-V=`
    would translate to `-I` exactly as it does for CPP2.

The honest summary: the flag is a small piece of work, the DEFS repair under
it was the real blocker, and neither is what stops gtar.

# 2026-08-23, the GCC flag — built, and mtools with it

rdoggett: *"I already told you to try the gcc solution. Please do it."* Fair.

## The flag

`GCC` in a recipe compiles every source with `gcc2 -c -o ctmp_<base>.r` and
links with **l68 by hand**. Four things about it are not guessable:

  - **gcc2 PREDEFINES OSK, _OSK, __OSK__ and mc68000**, so the path does not
    pass `-DOSK`. It also means `-U_OSK` CANNOT WORK: gcc2 puts user options
    ahead of its own `-D`s on the cccp2 line, and `-Wp,` is silently dropped
    by this version. Anything hidden behind `#ifdef _OSK` is unavoidable.
  - **The link cannot be gcc2**, because the module then takes its name from
    the output FILE -- and we write `R_<prog>`, so every module would call
    itself `R_<prog>` in its own usage text. That is the exact fault `-n=`
    exists to prevent. `gcc2 -v` shows it running `l68` anyway, so the path
    runs l68 itself and adds `-n=`. Measured: gcc2 gives a module named
    `R_wl`, l68 `-n=` gives one named `named`.
  - **THREE COPIES OF THE MERGED LIBRARY, UNDER THREE NAMES.** l68 makes one
    pass per DISTINCT library FILE; repeating `-l=x.l` buys nothing, which is
    not what the failure table implied. mtools' codepage.c calls `strtoul` and
    its missing_functions.c defines `strerror`, both after their callers.
  - **SRC/COMPAT is opt-in here** (`-V=/h7`), not automatic. It exists to fill
    gaps in Microware cc's headers; GCC brings its own and COMPAT shadows
    them. But GCC has no `<limits.h>` at all, so trees do still ask for it.

`-M=64k` and anything else in the extra field now reaches l68.

## Four DEFS headers repaired — gcc2 was unusable without this

`DEFS/GCC2` is ten headers laid over the SDK's set, and they disagreed:

  - **stdlib.h** declared `extern int isalnum(char c);` and fifteen more that
    the SDK's `<ctype.h>` defines as MACROS, and pulled in a `<direct.h>`
    needing a `WORD` typedef. Guarded, and given the `size_t`, `RAND_MAX` and
    `MB_CUR_MAX` it never had.
  - **stdio.h** was GNU's, written against GNU libio: `#define stdin _IO_stdin`,
    `#define getc(fp) _IO_getc(fp)`, and its own comment said `/* TODO */`.
    **No library on this disk provides any of those symbols** -- gcc2 links
    Microware's clibn.l, whose streams are `_iob`. Any program that so much as
    named `stderr` failed at the link; printf-only programs worked, which is
    why it went unnoticed. It is a forward to the SDK's `<stdio.h>` now.
  - **errno.h** used eleven `EOS_` names -- Ultra C spelling -- that nothing on
    this disk defines, to define `EACCES`, `EPERM`, `ENOTDIR` and the rest.
    Aliased to the SDK's `E_` codes. Ten map exactly; `EOS_BPNNF` has no
    counterpart and is aliased to `E_PNNF`, which is a judgement call and the
    only one.
  - **SRC/COMPAT/stdlib.h** gained the same three ANSI items, because on the
    GCC path it shadows GCC's own.

A two-line program -- `#include <ctype.h>`, `#include <stdlib.h>`, `main(){}`
-- did not compile before this. **That is very likely why `ls` was "repaired"
rather than rebuilt and why `mtools` and `lua` were written off**: nobody had
tried the disk's gcc2 on something small enough to see why.

## mtools BUILDS

45 sources. It runs: `mdir -?` prints the real mtools 3.6 usage, and `mdir`
reaches for `/pc1@`, the PC floppy descriptor, which is right when none is
configured. The recipe's note lists every flag and why.

Two source-side corrections, both marked in place and neither a compiler
workaround:

  - `config.h` claimed `HAVE_STRERROR`. It is `configure` output from the
    machine the port was built on. This system has no strerror in any library
    a trap-free link can reach, and the claim only stopped mtools' own copy
    from being compiled. **This is what a config header is for.**
  - `sysincludes.h` declared `void atexit()` under `_OSK` while mtools' own
    `missing_functions.c` defines `int atexit()` twelve lines in. The package
    contradicts itself; the OSK arm assumed libgcc2 would supply atexit and
    the libgcc.l here does not. It fails the same way for any toolchain whose
    libgcc lacks it.

`shims/os9strtol.c` gained `strtoul`.

## lua and luac — closer, and both blocked on absent material

Not recipes, because neither links. But the compiler is no longer the issue:

  - **luac: all 17 sources compile.** It stops at the link on `_os_crc`,
    `_os_ss_attr` and `_os9_id` -- Ultra C's syscall wrappers. `os_lib.l` has
    them and `l68` says it is "not a relocatable module", same as `ppplib.l`.
  - **lua: 16 of 17.** `lua.c` has `#ifdef _OSK #include "ldblib.h"`, and
    `ldblib.h` is in no copy of the tree. gcc2 predefines `_OSK` so the arm
    always fires -- under Microware cc it never did, which is why this never
    surfaced before.
  - Both need `/dd/ucc/defs/types.h`, an absolute path into the porter's Ultra
    C layout, plus a `process_id` typedef. `make_overlay.sh` creates a
    stand-in **in the overlay only** -- a `ucc` directory on the shipped disk
    would read as Microware's Ultra C being installed here.

### And a regression the full build caught

Adding `strtoul` to the shim broke `ed`, which had been building. The shim
uses `ULONG_MAX`, and `SRC/COMPAT/limits.h` -- written earlier the same night
-- spelled it `4294967295UL`.

**Microware c68 does not understand the `U` or `UL` integer suffix.** It reads
the letters as an identifier: `undeclared identifier`, then `syntax error`.
`L` alone it does accept, which is why `strtol` had been fine and only
`strtoul` exposed it. Both `UINT_MAX` and `ULONG_MAX` are hex now -- same
value, no suffix, and still usable in a `#if`.

That is the fourth whole-tree build of the night and the second to catch
something no single-recipe test could. The rule holds: a fix verified on one
recipe is not verified.

# 2026-08-23 — ls: it compiles, and it must NOT be adopted

rdoggett: *"ls is a critical resource ... If you can get the source to
compile, and it's the same or better ls, it's worth doing. People without an
os9 disk who want to try this collection with os9exec absolutely need ls."*

**It compiles. It is worse. So it is not adopted, and there is no recipe.**

## What the comparison showed

Same directory, same files, one with `chmod 400`, one `chmod 755`, one dated
1993, and a subdirectory.

    ls -l   SHIPPED BINARY                    THIS BUILD
            -r--------  a.txt                 bus error, TRAP 2
            -rw-r--r--  b_longer_name.dat     (E_BUSERR, in ls edition 7)
            -rwxr-xr-x  big.bin
            -rwx--x--x  ls_new
            drwxrwxrwx  sub
            real per-file modes, real dates
            including `Dec  3  1993'

Bare `ls` differs too: the shipped one lays out columns, this build prints one
name per line.

## Why, and it is not the compiler

`notes/FREEWARE-REBAKE.md` said `SRC/ls` is the PRE-FIX tree. That is exactly
right, and this is the measurement behind it. `SRC/ls/os9stubs.c` fabricates:

    buf->st_mode = S_IFREG | S_IRUSR | S_IXUSR | S_IROTH;

-- one fixed value for every regular file -- and never assigns `st_mtime` at
all (`grep -c st_mtime` is 0). The shipped binary prints per-file modes and
real timestamps, so it was built from a LATER source that reads the real
attributes.

**That source is on no disk here.** `disk/SRC/ls` and
`play/oskBoot/SRC/ls` are byte-identical apart from line endings, both
pre-fix; there is no other `os9stubs.c` or `filemode.c` anywhere under
`~/Developer/os9`, and the salvage tree's `src2/ls` holds an empty `sys/`.
The shipped binary is the only artefact of the fixed source that survives.

## What the attempt was worth anyway

Getting that far exercised the new GCC path hard and produced three fixes that
stand on their own:

  - **An include cycle in SRC/COMPAT.** `SRC/ls/sys/stat.h` says
    `#include <stat.h>` to reach the system header; `COMPAT/stat.h` said
    `#include <sys/stat.h>`. With both on the path they call each other and
    **cccp2 recurses until it dies with `**** Stack Overflow ****`** -- which
    reads like a broken source file and is not one. `COMPAT/stat.h` includes
    `<UNIX/stat.h>` directly now, which is where it was going anyway.
  - **`shims/os9isgraph.c`.** `isgraph` is in `csl.l` and nowhere else, and
    csl.l needs the trap handler a trap-free link does without.
  - **`DEFS/os9lib` is usable from the GCC path** -- it is ANSI-era, which
    made it a dead end for `c68`, and it is the only place on this disk with
    `uid_t` and `S_IRUSR`. It needs an `/h0`, because `os9lib/time.h` includes
    `</h0/defs/setsys.h>` by absolute path. **Mounting the overlay as
    `OS9H0` as well makes the whole set work** -- that is a one-line change to
    `run()` in rebuild.sh, and it is NOT in the tree because no recipe needs it
    today. It is the first thing to try for gtar, whose missing `TRUE`,
    `FALSE`, `ERROR` and `S_ISUID` all live in os9lib.

## If anyone wants ls from source

The build works; only the stubs are wrong. `os9stubs.c`'s `stat()` needs to
read the real file descriptor -- `_gs_gfd` gives the FD sector, which carries
the attribute byte and the modification date -- and set `st_mode` and
`st_mtime` from it. The recipe that compiles the rest is:

    ls|ls|ls.c argmatch.c error.c filemode.c getopt.c idcache.c obstack.c
       os9stubs.c savedir.c xmalloc.c xstrtol.c|GCC HAVE_CONFIG_H||
       -V=/dd/DEFS/os9lib -V=/h7 -M=32k

with the `/h0` mount above. Until the stubs are fixed, **the shipped binary is
the better program and stays.**

# 2026-08-24 — gtar builds, reads and extracts; and the ls key was found

rdoggett: *"yes, gtar is fine"*.

## It builds, through the GCC flag

Six walls, not the one the notes blamed. The cpp bus error was only the first;
`notes/CPP-MACRO-CRASH.md` had already cleared it, and everything below was
behind it. The recipe's own note lists every flag; the short version is that
GNU tar was written for gcc, and once compiled by gcc the ANSI prototypes,
long lines and the rest stop mattering.

**The three K&R edits this session made to gtar on 2026-08-23 are REVERTED.**
They were compiler workarounds, exactly as rdoggett suspected, and gcc2 does
not need them. `create.c`, `list.c` and `buffer.c` are the archive's own again.

## What it can and cannot do -- run, not inferred

**Reading and extracting work, and that is the point.** Given a ustar archive
built on another machine, `gtar -tvf` lists it with correct modes, owners,
sizes and dates, and `gtar -xvf` extracts all three test files
**byte-identical**, including a 3000-byte binary. Somebody who downloads a
`.tar` now has something that opens it.

**Creating archives is wrong, and gtar says so on every file:** `file X shrunk
by 720880 bytes, padding with zeros`. Cause, measured: `os9lib.l`'s `stat()`
fills os9lib's OWN `struct stat`, and what gtar has in scope is the one from
`DEFS/UNIX` by way of `SRC/COMPAT`. **Both are 36 bytes**, so nothing is
overrun -- the fields simply land in the wrong members, and `st_size` comes
out as 720897 for a four-byte file. It also makes every file look like the
archive itself (`src is the archive; not dumped`), because st_dev and st_ino
land on the same garbage for everything.

## THE KEY FINDING, and it is the one ls needs

Pair os9lib's `stat()` with **os9lib's own `<stat.h>`** and it is correct.
Measured with a five-line probe on two files and a directory:

    f1   ino=3108864  size=4   mtime=1787549940   (four bytes, right)
    f2   ino=2079232  size=8   mtime=1787549940   (eight, and a DIFFERENT ino)
    d1   ino=2318336  size=64  mode=0177677       (directory)

Distinct inodes, real sizes, a real modification time. **That is everything
`SRC/ls/os9stubs.c` fabricates**, available from a library already on the
disk -- so the ls question may not need the lost source at all: it may need
`os9stubs.c` deleted and os9lib's stat used instead, with os9lib's header.

**What stops it here**: with the os9lib headers in scope, gcc2's `cc2` dies
with a fatal signal on `port.c` -- both message arms, and port.c hardcodes
`#define VARARGS_MSG` at line 103 so the recipe cannot choose. That is a
compiler bug on one file, not a design problem, and it is the whole distance
between gtar-as-reader and gtar complete.

**A wrong turn worth recording**: `SRC/COMPAT/varargs.h` was changed to hand
gcc its own `<stdarg.h>`, on the reasoning that GCC passes arguments in
registers and Microware's varargs cannot describe that. It is true and it
still broke the build -- GCC's `stdarg.h` has a TWO-argument `va_start`, and
K&R varargs code calls it with one. Reverted. The original header was right.

## Also

`SRC/COMPAT` gained `errno` in `stdlib.h` (gtar's create.c declares it itself
under `#ifndef OSK` and, under OSK, relies on stdlib.h -- the porter's had
it, neither the SDK's nor os9lib's does), a `<stdio.h>` ahead of the forward
in `grp.h` (os9lib's declares `fgetgrent(FILE *)`), and `major`/`minor` that
cast through `unsigned long` because OS-9's `dev_t` is a `char *` -- a device
NAME -- so shifting it directly is `invalid operands to binary &`.

Two new shims: `os9ftime.c` (blarslib carries an ftime.c but it is one of the
four objects blarslib does not build) and `os9sswfm.c`, a stub for the tape
`SS_WFM` SetStat, which exists only in `LIB/tape.l` -- a file `l68` rejects as
"not a relocatable module", like `os_lib.l` and `ppplib.l`. `os9geteuid.c`
gained `unix_getuid`, which gtar's names.c calls under `#ifdef OSK`.

**The bootstrap was a real chicken and egg** and it is worth knowing why it
existed. `make_overlay.sh` puts `ansi2knr` into the overlay by copying it out
of `built/`; `built/ansi2knr` only exists once a build has made it. On a fresh

## cio-linked binaries are the default now

*"you should produce (smaller) binaries that require cio/csl/math, right?"*

Right, and the saving is larger than expected. Same source, same overlay:

    ascii    14286 bytes trap-free  ->   2608 with cio     -82%

### Three linkages, and the smallest is not always available

    -qm     14286 bytes   clibn.l + math.l   stands alone
    -qxm    10022          clib.l            uses the math trap
    -qixm    2610          cio.l + clib.l    uses cio and math

**`-qixm` breaks thirteen of 290**, and `CLAUDE.md` already said "never
-qixm". Now the reason is measured: `cc` hands l68 BOTH `cio.l` and `clib.l`,
and this SDK's `clib.l` is not a reduced library -- 38667 bytes against
`clibn.l`'s 38523, so it still has `printf` and `time`. Whether that collides
depends on which members l68 happens to pull. `banner` links; `joke` stops
with `Symbol printf from psect cio_a ... caused name clashes`.

So the driver takes the best each program can have: try `-qixm`, and if the
link reports duplicate symbols step down to `-qxm` (which still saves a
third), then to `-qm`. Each step at most once, and only while no module has
been produced. `TRAPFREE` in a recipe forces the standalone build.

`-qxm` needs `math.l` added by hand, incidentally: `-x` says "reach the math
library through traps" and l68 still wants `_T$LtoD` and friends resolved at
link time. `robots` found that.

**This moves nothing on the shipped disk.** The driver installs nothing, so
`DOC/INDEX`'s star grid is untouched until somebody installs a rebuilt module
on purpose -- and at that point the star list must be RE-MEASURED by running
every program against a disk with cio removed.

**A check that could not fail, again.** Confirming which binaries need cio by
byte-searching them for the module name reports "no" even for `cat`, which is
starred. `CLAUDE.md` already says never to use that proxy; it was tried anyway
and it is still wrong. Only running them settles it.

`make_overlay.sh` copies `disk/DEFS` into the overlay but SKIPS any file the

SDK one. That rule also silently discarded the four `DEFS/GCC2` headers
repaired earlier in this session. They only ever worked because they had been
hand-copied into a live overlay; a clean one had the originals back, and
thirteen builds changed behaviour with no edit to blame.

A header under `disk/DEFS` carrying the marker `osk-freeware` now overrides
the SDK's copy, and `make_overlay.sh` says how many did:

    added 17 header(s) from the collection's own DEFS
    ...3 of them replacing an SDK copy, marked osk-freeware

**2. `TRAPFREE` did nothing.** It was parsed out of the defines field into a

recipe runs it, and it should depend on as little as possible.
