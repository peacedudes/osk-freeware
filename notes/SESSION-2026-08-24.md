# 2026-08-24 — ls, gtar, C++, assembly, and a bug the rebuild found

Branch `release-pass-2026-08-21`. Every commit made with all eleven
`check_disk.py` checks green.

## ls builds from source and is installed

The one change to a shipped binary this session, and the one the user asked
for by name. `disk/CMDS/ls` is now built from `disk/SRC/ls`.

The rule was same-or-better. Measured over 40 option cases against the binary
that shipped — `-l -lt -lS -lR -C -x -m -1 -a -F -d -p -s -k -Q -b -o -g -n
-w -T --full-time --help`, two directories at once, a missing path, and the
whole of `/dd/CMDS`:

    39 of 40 byte-identical
     1 better: `ls -i' printed 0 for every inode. It prints real ones now.

Three defects, all in the source, all marked and dated:

  - **`os9stubs.c` fabricated `stat` and `fstat`.** One mode for every file,
    `st_mtime` never set. `os9lib.l` has real ones, so ours are gone and the
    recipe links `/dd/LIB/os9lib.l`.
  - **os9lib's `stat()` sign-extends the attribute byte.** A directory
    (`0xbf`, bit 7 set) arrives as `0xffbf`; a plain file (`0x1b`) as
    `0x001b`. `system.h` tested type through an `S_IFMT` of `0x0380`, which
    matched the sign fill, so `S_ISDIR` was false for every directory on the
    disk and `ls -l /dd/DOC` printed the directory instead of listing it.
    Only the low byte means anything, and in it only bit 7 says anything
    about type — OS-9 has no separate regular-file bit.
  - **`filemode.c` never included `system.h`.** It rendered OS-9's attribute
    bits through Unix's `0777` layout and printed `d--S--S--T` for every
    directory, the `S`s and `T` coming from os9lib's setuid, setgid and
    sticky bits, none of which OS-9 has.

`DOC/INDEX` said the source for `ls` was "on the h0 workshop disk"; that is
corrected. It still says so for `cat`, `wc`, `basename` and `dirname`, and
that is still true — searched this repo and `~/Developer/os9/Scraped`, and
they are in neither.

## gtar creates archives correctly

`gtar -cf` over `/dd/SYS`, extracted host-side: **809 files, all
byte-identical**, binaries included. Listing and extraction on the OS-9 side
work too. Yesterday's note said creation wrote nonsense sizes; that was this
recipe's build, not the shipped `CMDS/REBUILT/gtar`, which is an archive
binary and always worked. **Nothing was installed** — ours is 130868 bytes
against its 113562 and behaves the same, so there is nothing to gain by
swapping it. What is new is that the recipe reproduces it.

`cc2` had been dying on `port.c` whenever os9lib's headers were in scope.
The cause: os9lib defines `bcopy`, `bcmp` and `bzero` as MACROS in
`<bcopy.h>`, which its `<types.h>` pulls in, and port.c's `USG` block defines
functions of those names straight into them. gcc2 predefines `OSK`, so the
guard costs the recipe nothing.

Two shadow headers were needed, both in `disk/SRC/COMPAT/OS9LIB`, and the
`-V=` ORDER is load-bearing — see `tools/rebuild/README.md`.

## The disk can build C++

Proven end to end: a class, a constructor, a method call, compiled, linked
and run. Four things had to be found:

  - `gcc2` cannot start the C++ front end at all — no `.cc` in its suffix
    table, it calls one a "linker input file". Only `gpp` can.
  - `gpp` forks `cccp`; the disk ships that preprocessor as `cccp2`.
  - `collect` is in `CMDS/GCC2`, not `CMDS`, and nothing with a global
    constructor links without it.
  - `collect` opens `gpp.l`; the disk ships it as `libgpp.l`.

`make_overlay.sh` supplies all three names now and `rebuild.sh` has a `GPP`
flag. **No recipe uses it yet** — the only C++ here is `homelibr`, and that
needs a port rather than a recipe. Blockers written up in `COMPILE-AUDIT.md`.

A user of the disk cannot compile C++ either, for the same reason, and two
byte copies (256K total) would fix that. Not done: `disk/CMDS` is not to be
touched without rdoggett, and it is question 2 in `FOR-RDOGGETT.md`.

## aterm assembles, byte-for-byte

`rebuild.sh` has an `ASM` flag. `aterm` builds through it and the module that
comes out is **identical to the shipped binary, all 13422 bytes**. The trick
was `-l=/dd/LIB/os9.l -l=/dd/LIB/sys.l`: ATerm names 53 symbols it never
defines and Microware's assembler definitions file is not in this SDK copy.
`MODNAME=` sets the module name, and its case matters — `-n=aterm` differs in
five bytes, two of the name and the three CRC bytes after it.

`serload` and `graph` cannot be assembled: `rt_comm/`, `graphmakros` and
`mathmakros` are in neither this repo nor the pool.

## A bug that only a rebuild could have found

Rebuilding `msdir` and running it beside the shipped one:

    shipped        1 file(s)               139 bytes
    rebuilt        1 file(s)      bytes

`mdir.c`'s `dotted_num()` does `sprintf(buf, "%.*ld", 26, num)` — asking
printf to pad an INTEGER to a precision. **No C library on this disk does
that.** Measured, all four: `clibn`, `clib`, `cio` and `os9lib` each answer
`139` for `%.26ld`. `len` then comes out 3 and the function returns
`buf + 3 - 13`, ten bytes before its own buffer.

That is the C standard's behaviour missing from every library here, not a
mistake in the port. Fixed by doing the padding by hand, marked. `msdir` now
prints output identical to the shipped binary.

**It also means the `mtools` recipe was producing a subtly wrong binary and
reporting `clean`.** Worth remembering what `clean` means in `build.sh`: it
compiled and linked. It is not a claim that the program works.

## Counting, and a number that was too high

`tools/src_census.py` is new — the source-coverage figure as a tool, because
the old one (390 of 938, 42%) was taken by hand and could not be re-derived.

Its first version said 43%, and that was wrong: matching any `<program>.c`
under `SRC` made `CMDS/names` match gtar's `names.c` and `CMDS/t` match a
two-line `t.c` in `SRC/ls`. Requiring the file to actually define a program —
a `main()`, or for assembly a `psect` with a non-zero type — drops it to
**389 of 937, 41%**, and independently agrees with `CLAUDE.md` about
`basename` having no source here. The figure is a floor: a program whose
`main` lives in a differently-named file reads as having none.

`tools/module_census.py` also corrects a stale claim. It is not 7 modules
reporting a name that is not their filename, it is **63** — and 61 of those
are the original author's own capitalisation (`ATerm`, `AtoB`, `FStat`,
`wermit`) and should be left alone. Exactly two are ours, both from a rebuild
pass that forgot `-n=`: `REBUILT/compress` and `REBUILT/screen`. Neither can
simply be rebuilt and swapped — the current recipes do not reproduce them —
so that owes a behaviour comparison first.
