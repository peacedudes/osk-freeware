## What the emulator did wrong: nothing yet

Two things looked like emulator faults and are not:

- **`cpp` bus-errors on nested macro expansion.** Reproduction and the two
  nearest non-crashing cases are in `notes/CPP-MACRO-CRASH.md` and
  `notes/cpp-macro-crash/`. It is a fixed-size buffer being run past inside
  Microware's `cpp` — more process memory changes nothing, and the register
  dump has ASCII where a pointer should be. os9exec's part is to report it,
  which it does cleanly and with enough of a dump to diagnose. `flex` is the
  one program here that hits it.

- **`cc` emitting 161 MB of "source line too long"** while compiling GNU
  `ed`, which wedged the build driver for five minutes with no os9exec
  running. `ed.h`'s `REALLOC` macro joins into one logical line of about 1400
  characters. The driver now bounds what it captures, so this costs a line in
  a log rather than an unexplained hang.

## What was actually broken, and is now fixed

**Every build dirtied `disk/`, and `mkimage.sh` reads `disk/` off the
filesystem.** Each recipe compiles in place, so a build immediately before an
image build shipped 77 object files, five `ctmp.*` temporaries cc left behind,
and fourteen of the ARCHIVES' OWN `.r` files overwritten by ours. A tenth
check (`no build products in the tree`) now refuses it, and it caught a
`ctmp.000003.o` that had been committed and was shipping. `tools/build.sh`
moves the modules to `built/` and puts the tree back as it found it.

**The OS-9 shell truncates a command line at about 600 characters, silently.**
`mtools` has 45 sources; its `cc` line ran to 900 and what arrived was cut
mid-option. The error that came back was `can't open /dd/DEFS/stdlib.h`, which
reads exactly like a missing header. `rebuild.sh` now measures the line it is
about to type and, when it would be too long, compiles each source separately
and gathers the objects with `merge -z=<file>` — which takes its list from a
file and so has no limit.

**`l68` makes ONE pass over a library.** A member calling another member
further down the file is left unresolved: zoo's `huf.c` wanted `putbits` from
`io.c` 24 times. The gathered library is now named five times.

**`cpp` will not find `<sys/types.h>` through `-V`.** Given an include name
with a directory in it, it reports `can't open /dd/DEFS/sys/types.h` and
stops. `make_overlay.sh` copies `SRC/COMPAT/sys` into the overlay's `DEFS`.

**`rebuild.sh`'s `$OS9COMPAT` default pointed at `freeware/SRC/COMPAT`**,
a path that has not existed since this repo was split out. Anyone calling the
driver directly rather than through `build.sh` got "can't open" for every
header COMPAT supplies.

**The shim retry added exactly one shim and gave up.** `lwf` wants `getpwuid`
AND `popen`. It now keeps adding while each round names one it has not tried,
and removes them from the tree afterwards — a shim left behind in `disk/SRC`
would ship as if the port had always carried it.

## Port defects found and fixed

- **zoo**'s OSK section of `options.h`: `VARAGS` for `VARARGS`, `NEED_MEMOVE`
  for `NEED_MEMMOVE`, and a `NEED_MEMSET` that clashes with `clibn.l`. Note
  the asymmetry, which is the whole reason this took three passes: `clibn.l`
  has `memcpy` and `memset` but **no `memmove`**. So memset must be off and
  memmove must be on, and the archive had them exactly the wrong way round by
  typo.
- **lwf**: `<time.h>` is behind `#ifdef OS9`, and `R_OK` is access()'s read
  bit, which OS-9 spells `S_IREAD` = 1, not the Unix 4.
- **ccheck** wants `-DUNIX`; its own header says so.
- **adv**: the tree carries three files with `main()`. Its makefile's `RFILES`
  is the right list and always was. This closes the item that "got away".

## New

`disk/DOC/START-HERE` — a dozen programs that run with nothing set up, and how
to get back out of each. This was the one capability rdoggett named that had
no tool behind it: `about` answers *tell me about X*, and nothing answered
*show me something worth typing*. `disk/readme` points at it.

`tools/rebuild/shims/os9alib.c` — `strucmp`, `strnucmp`, `strstr` and
`rename`, all of which SECAD's `alib.l` supplied and which is not here.
Read that file's note on `rename` before trusting it: `os9lib.l` has a real
one, but its psect also defines `copy`, which dm's `misc.c` defines, so the
shim copies bytes and unlinks instead. Not atomic, and a new file rather than
the same one renamed. Every caller here renames a file it has finished with.

## What was missing, and where it turned out to be

The question rdoggett asked at the start -- *figure out what is missing, then
look for it* -- had an answer nobody had asked for: **the import read the
usenet archives only partly.** Three programs that had been failing to build
for want of a file were fixed by opening the archive they came from.

  - **world** failed on `can't open parame.inc`. That file is not meant to
    exist: `vcnvrt` generates it from `vocab.dat`, and `vtxtcn` generates
    three more from `vtext.dat`. Neither data file was in `SRC/world`. Both
    were still in `play/h4/ARR/world.ar`, `vtext.dat` in three pieces split on
    line boundaries. `SRC/world/README-RECOVERED` has the detail. The old
    recipe was called `convert', which is not a program at all -- it is a
    `touch`ed timestamp in the makefile.

  - **patch** failed on `can't open config.h`. That is the output of patch's
    `Configure` script, which was never going to run on OS-9, and the archive
    carried it ready-made as `config.H`.

  - **sonnet** failed on `can't open lex.i`, which `makelex` builds from
    `lex.data`. Both were here; nobody had run the one command.

`tools/missing_from_archive.py` is that search generalised: for every tree the
disk carries, it opens the archive `DOC/ORIGINS` names and lists the members
that did not make it in. It PROPOSES and copies nothing -- some absences are
deliberate. It compares against the whole of `disk/`, not just `SRC`, because
a game's data lives under `GAMES` and its manual under `DOC`.

## Still open

`tools/build.sh --missing` is the live list. Known-blocked, with reasons:

  - `flex`  — the `cpp` crash above.
  - `ed`, `lout` — ANSI C built with gcc. GNU `ed` also wants `const` and a
    macro `cpp` calls too long; `lout`'s `externs` uses typed bitfields.
  - `rcs`   — **source genuinely incomplete**: `rcssyn.c`, `rcsrev.c` and
    `rcsutil.c` are missing, and they are missing from `rcs4.lha` in the pool
    too, so it is the archive and not the import. This is RCS **version 4**
    (Purdue, 1987), not 5.x — GNU's `rcs-5.7` files are NOT drop-in. Finding a
    comp.sources.unix volume-12 mirror would fix it; two tried on 2026-08-22
    were gone.
  - `pep`   — wants an EPROM `standby`.
  - `COMPAT`, `unixlib` — not program trees. `unixlib` builds a LIBRARY
    (`unix.l`) and there is no path for that yet; its own makefile shows the
    shape (`merge -b99 -z=lib_list`).
