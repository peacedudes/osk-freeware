## The find: `pep` was a name collision, and it builds now

`tools/rebuild/recipes.psv` read `pep|effo_wolk|pep.c|||`. That source is a
German EPROM programmer — *"pep.c Programmiert das Eprom von startadr bis
endadr"* — which wants an EPROM board and has never built. It is not what
ships. `disk/CMDS/pep` answers `Copyright (c) 1989 Gisle Hannemyr` and is the
file 'detergent', which is what `DOC/INDEX` has always said it was, and its
source has been sitting in `disk/SRC/pep` the whole time.

Repointed. It now builds clean and verifies, and the rebuilt module's output
is **byte-identical to the shipped binary** on `-h` and on a tab-expansion
run over a mixed CRLF/tab file.

One source change was needed, in `disk/SRC/pep/pep.h`, marked and dated:
OS-9 was never one of the four systems that header knew, so `DIRCHAR` was
undefined and `plain.c` would not compile. Defining `__UNIX__` also works and
was tried first — it is wrong: `main.c` sets `EndOLn = '\n'` under `__UNIX__`,
and on OS-9 `'\n'` IS CR, so pep announced *"terminating lines with CR"* where
the shipped binary says CRLF. That one line was the only difference between
the two builds, which is how it was caught. An `#ifdef OSK` branch keeps the
shipped behaviour exactly.

`rename()` comes from the `os9alib` shim; the driver adds it by itself.

**That was one of the two recipes described as permanently failing.** The
other, `pdraw`, still wants X11 headers. The whole-tree figure has not been
re-measured.

# Later the same day — both open questions answered

## 1. pep's tables: `/dd/SYS/PEP`, and it is wired up

**Where pep looks, read out of `plain.c`'s `readtable()` rather than guessed:**
exactly two places, and no more. The `-g` name as given (relative to the data
directory), then `$PEP/<name>`. The third candidate in the source, a directory
derived from `argv[0]`, is `#ifdef __MSDOS__` and never runs here.

So it is the same shape as `TERMCAP`, and it is now set the same way:

    disk/SYS/PEP/           the seven tables
    disk/SYS/login          PEP=$ROOT/SYS/PEP, and PEP added to the export
    disk/SYS/profile        PEP=/dd/SYS/PEP        (bash's system-wide file)
    disk/local/sys/profile  the same file, second copy
    disk/startup            setenv PEP /dd/SYS/PEP, with the why beside
                            TMACDIR/HELPDIR/SIMPATH

Verified end to end on a freshly built image, through `bash /dd/SYS/login`
with nothing set by hand: `pep -gibm2iso` finds `/dd/SYS/PEP/ibm2iso` and
converts CP850 `\x82 \xa5` to ISO 8859-1 `\xe9 \xd1` (é, Ñ). Correct.

`DOC/pep` also gained the archive's own `aaaread.me` (the release note, which
is what lists the tables) and `pep.1l` (the nroff manual source).

| program | builds | runs | verdict |

**`card`** — Istvan Mohos, 1984, "Christmas Card From Hanoi". Draws a greeting
with VT100 cursor positioning; it wants `TERMCAP` set and says
"bad or missing termcap... but MERRY CHRISTMAS !" without it, which is a

**`ttyexp`** — Dennis Lo's explosion screen-clearer. It draws a real fireworks
display and ends by clearing the screen and exiting of its own accord.
One repair was needed and it is the archive's, not ours: the README at the top
of the file sits BETWEEN two closed comments, so `Here's` is code and c68 stops

whole fix.

**`marquis`** — scrolls a message on the terminal's STATUS LINE, and stops with
"terminal doesn't have status line capabilties." **No entry in
`disk/SYS/termcap` has `hs` at all** — measured, zero — so on anything this
collection ships it can only refuse. That is not a port problem and there is
nothing to fix.

**`travesty`** — Daniel J. Bernstein's Markov travesty generator, and the one
that is genuinely worth wanting. It builds (its `optind` wants a getopt;
`SRC/unixlib/getopt.c` serves) and it starts: `-A` prints the author, so option
parsing works. **But its output is wrong — it reproduces its input verbatim**,
at order 1 as well as order 4, which no Markov process does.

  The control that settles it: the SAME source built natively on the host
  produces a proper travesty ("the multiple followindow and Buffer offered
  output and a bufferredefined function"). So the algorithm is sound and the
  OS-9 build is what is broken.

  Randomness is NOT the cause, which was the first guess, because the file's
  own build line names `-l=/dd/lib/rand.r` and that object is not here. A
  five-line probe shows `randint()` resolving from `LIB/unix.l` and returning
  properly varying values.

  What this copy IS, is damaged. Its `#ifndef OSK` arm contains a bare
  `else seed = 0;` with no `if` — the porter deleted a line — and it compiles
  for us ONLY because the damage is hidden behind the `#ifdef`. The host build
  will not compile until that is repaired. A source in that state should be
  assumed damaged in the OSK arm too.

**`porsche`** — displays a bitmap on a KT7 terminal. Its edition history reads

## Two defects found on the way, one fixed

**`tools/rebuild/shims/os9randint.c` could never have compiled.** It was the
only shim written with LF line endings; c68 reads it as one enormous line and
stops with `bad character`. Converted to CR, like its twelve neighbours, and
proved: it now compiles.

And having compiled, it reveals the second thing — **`LIB/unix.l` already has
a `randint`**, in psect `rand_c`, so linking the shim into any build that uses
the `-qm` linkage fails with `duplicate symbol names`. The shim is only of use
to a build that does not link `unix.l`. Both facts are now written into the
file's own header, because neither is visible without trying to use it. This
is also why nobody noticed: `rebuild.sh`'s shim table has no case for
`'randint' unresolved`, because randint never is.

# Later still — `card` was NOT working, and both are now installed

## The correction

I reported `card` as working. **It was not.** The 60-second run I judged it on
was cut off by my own timeout before the failure. Run to completion it dies
with a **bus error** — `vector=$02`, `Last syscall: I$WritLn`, `A2=20682E88`,
a wild pointer read out of the middle of a string — about forty moves into its
animation. Reproducible, every time.

This is the trap this collection keeps producing, in its purest form: a check
that could not fail, because it never ran long enough to. `notes/` already
says "make every check fail once before believing it"; a truncated run is a
check that has not been given the chance.

`ttyexp` was and is fine — three runs, identical output, clean exit each time.
I could not give either program a real terminal (`script` cannot get a
controlling tty in this session), so all of this is pipe-based. The failure
and the fix both show up the same way through a pipe.

## What was actually wrong, and the flag it needed

`card` calls `tputs`/`tgoto` itself. **Every library that carries the terminal
globals — `PC`, `UP`, `BC`, `ospeed` — carries its own copy**, and the driver
links `curses.l` AND `termlib.l` at every linkage. One copy gets initialised,
the other gets read, and the result is the wild pointer.

Its own build line says so: `cc -qm=2k card.c -l=/dd/lib/termlib.l`. Termlib
alone, and trap-free. **Both halves are needed** -- measured separately:

    curses.l + termlib.l, -qixm     bus error at ~40 moves
    termlib.l alone,      -qixm     bus error at ~40 moves
    termlib.l alone,      -qm       7,697,435 bytes, 4095 moves, clean exit

So `TRAPFREE` was not enough and `NOCURSES` was not enough; together they work.

**`NOCURSES` is a new recipe flag** in `tools/rebuild/rebuild.sh`, documented
in its own comment there. One wrinkle worth knowing for the next flag: the
linkage-fallback loop REBUILDS `QMLIBS` from scratch for each of its steps, so
a flag that edits `QMLIBS` has to be applied inside that loop as well, or it
silently stops working on the retry -- which is the linkage most programs end
up with.

# Correction to the above: it was never curses, and it is not cio either

rdoggett asked why termlib or `-qixm` would cause a bus trap, and whether we
are still using cio on purpose. Both halves of that question were right to
ask. **My diagnosis was wrong**: I had measured three of the four cells and
read a cause into the gap.

The missing cell, measured now:

| linkage | libraries | result |
|---|---|---|
| `-qixm=16k` | cio.l + clib.l, with curses | bus error ~40 moves in |
| `-qixm=16k` | cio.l + clib.l, no curses | bus error, same point |
| `-qixm=64k` | cio.l + clib.l | bus error, **same byte count** |
| `-qxm=16k` | clib.l alone | **runs to the end** |
| `-qm=16k` | clibn.l, with curses | **runs to the end** |
| `-qm=16k` | clibn.l, no curses | **runs to the end** |

So **curses.l is irrelevant** -- `-qm` works with it linked -- and so is stack
size. `NOCURSES` was a flag invented for a cause that does not exist; it has
been removed and `tools/rebuild/rebuild.sh` is byte-identical to what it was.

**And it is not cio's fault.** `-qxm`, which links `clib.l` alone, works. What
fails is `cio.l` AND `clib.l` in the SAME link -- which is exactly what
`rebuild.sh`'s own comment already describes:

> cc hands l68 BOTH cio.l and clib.l for -qixm, and this SDK's clib.l is not a
> reduced library -- it is 38667 bytes against clibn.l's 38523, so it still has
> printf and time. Whether that collides depends on which members l68 happens
> to pull.

For thirteen of 290 programs that collision is LOUD: `Symbol printf from psect
cio_a ... caused name clashes`, and the driver drops to `-qxm`. **card is the
same fault, silent.** Nothing clashes by name, so l68 links it happily and the
program ends up with two stdio implementations -- writing through a `FILE`
that nothing initialised, which is the wild `A2` at `I$WritLn`.

That is worth knowing beyond card: **a duplicate-symbol error is the loud
version of a fault that can also be silent**, and the silent version looks
like a broken program rather than a broken link.

**The cio policy is unchanged and correct.** cio, csl, math, math881 and
csl020 ship by Microware's permission, `-qixm` is a fifth of the size, and it
stays the driver's default. card takes `TRAPFREE` as a documented exception,
the way other recipes already do, and the recipe carries the measurement so
nobody re-derives it. The binary is byte-identical to the one already
installed -- because curses never mattered.
